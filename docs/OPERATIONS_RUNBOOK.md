# 運用・公開手順書

## 1. 基本方針

- 原則として変更は専用ブランチとPull Requestで行う。
- 変更前に目的、範囲、期待効果、副作用を提示し、必要な承認を得る。
- ユーザーの承認なしに画像品質や不可逆操作を完了扱いにしない。
- 公開記録の禁止事項は `HANDOFF.md` を適用する。
- `main` を直接書き換えたり、履歴を強制更新したりしない。

## 2. 開発環境

必要条件はNode.js 20以上である。

```sh
npm test
npm run serve
```

`npm run serve` はローカルホストの4175番で静的サーバーを起動する。LAN内のiPhoneから確認するときだけ次を使う。

```sh
npm run serve:lan
```

同一ネットワークのiPhone Safariから `http://<PCのLAN IP>:4175` を開く。実際のIPアドレスやSSIDはIssue、Pull Request、ログ、文書へ記録しない。

## 3. 通常の変更フロー

1. `main` の最新状態、未完了PR、Issue、Pages状態を確認する。
2. 変更目的ごとにブランチを作る。
3. 仕様変更なら、実装前に選択肢、初期値、出力例、保存データへの影響を確定する。
4. 実装と同時に自動試験を更新し、選択肢データと契約試験の整合を確認する。
5. `npm test` を実行する。
6. ローカルで影響範囲を操作確認する。
7. UIまたは操作変更なら393×852相当の確認後、iPhone実機Safariで確認する。
8. `package.json`、README、仕様書、品質ログの更新要否を判断する。
9. Pull Requestを作成し、テンプレートの全項目を確認する。
10. ユーザーまたは責任者のマージ・公開承認後にマージする。
11. GitHub Pagesの構築完了と公開資産を確認する。
12. 公開版のスモークテストを行い、結果を記録する。

## 4. 版管理

PWA版は `package.json` を正とし、Semantic Versioningを目安にする。

- PATCH: 文言修正や互換性のある小変更
- MINOR: 新項目、新しい選択肢群、互換性を保つ機能追加
- MAJOR: 項目構造や出力契約の大幅変更、互換性を壊す変更

試作方針により保存データを移行しない場合でも、利用者への影響をPull Requestへ明記する。

## 5. 保存形式変更

項目追加、削除、ID変更、値の改名により保存済み値が不正になる場合は次を行う。

1. 対象項目と新しい保存形式番号を決める。
2. `src/mode-config.js` の統合キーとスキーマ版を更新する。
3. 旧キーを削除するか、安全な移行処理を実装する。
4. 前回値、連動状態、初回起動、再読込を試験する。
5. READMEと仕様書へ利用者影響を記載する。

9.0.0では `7days:unified:last-values:v2` とスキーマ版`2`を使用し、名前付きプリセット機能を廃止する。既存プリセットのlocalStorageデータは削除せず、実行時に読み書きしない。前回値の自動保存は維持し、旧統合v1を優先して旧写真v8をフォールバックとする非破壊移行と、二回目以降に上書きしないことを試験する。

## 6. Service Worker更新

`sw.js` のキャッシュ対象ファイルを変更した場合は次を行う。

1. `ASSETS` に必要資産がすべて含まれることを確認する。
2. `CACHE` の版を必ず更新する。
3. オンラインで一度起動し、新Service Workerがactivateすることを確認する。
4. 再読込後に新しい版が表示されることを確認する。
5. オフラインで主要操作ができることを確認する。

古い表示が残る場合は、公開資産の版、Service Workerの状態、Cache Storageの順に調査する。

ローカル作業版9.0.0のキャッシュ名は `7days-v18` である。公開時は配信された `sw.js` の実値を確認する。

## 7. GitHub Pages公開

引き継ぎ時点では、GitHub Pagesは `main` ブランチの `/` を直接配信する。Actionsによるビルド工程はない。

公開後に次を確認する。

- Pagesの状態が成功になっている。
- 公開URLがHTTPSで開ける。
- `package.json`、`src/mode-config.js`、`src/unified-catalog.js`、`src/anime-shooting.js`、`src/outfits.js`、`sw.js` が意図した版である。
- 指示文のコピー結果がローカル版と一致する。
- 前回値の自動保存と再読込復元が動作する。
- 9.0.0では名前付きプリセットと撮影設定がUI、生成文、実行時アクセスに残っていない。
- ホーム画面追加とオフライン起動が必要な変更では実機確認も行う。

配信元やブランチ保護は変更され得るため、作業開始時にリポジトリ設定を再確認する。可能なら `main` への直接pushを禁止し、Pull Requestレビューと必須試験を設定する。

## 8. 公開版スモークテスト

最低限、次を1セットとして確認する。

1. 髪型、髪色、前髪、人物の特徴が画面最上部へ指定順で表示される。
2. 人物の特徴が60種類あり、初期値がクールである。
3. 身長、バスト、ウエスト、ヒップの範囲、初期値、表示値が仕様どおりである。
4. 身長変更で連動中の寸法だけが変わり、手動変更、個別復帰、全リセットが正しく動く。
5. 推定カップがUIと生成文で一致し、初期値がCカップ相当である。
6. 衣装タイプと構成の選択で適切な項目が現れ、上下分離、上下一体、下着だけ、衣装内の下着が自然文になる。
7. 110色の名称とカラーチップが選択できる。
8. 指示文が改行、重複、UI分類語句、撮影設定を含まず、コピー通知が表示される。
9. 名前付きプリセットのUIがなく、旧プリセットデータへアクセスしない。
10. 再読込後に前回値と寸法連動状態が保持される。
11. オフライン起動が必要な変更では通信を切って再確認する。
12. 旧データが存在する場合は初回だけ9.0.0形式へ移行され、二回目以降は新データを上書きせず、旧キーも残ることを確認する。

## 9. 障害対応

### 公開版が更新されない

1. Pagesの最新デプロイと配信元を確認する。
2. 公開された `sw.js` のキャッシュ名を確認する。
3. キャッシュ名を更新し忘れていないか、統合画面の実行資産がすべて事前キャッシュされているか確認する。
4. 修正は新しいPull Requestで行い、再公開する。

### 指示文が仕様と違う

1. `tests/unified-prompt.test.mjs` に期待値があるか確認する。
2. `unified-catalog.js`、`catalog.js`、`anime-shooting.js`、`outfits.js` の出力値とUIラベルを区別して確認する。
3. PWAとGPTのどちらが原因かを切り分ける。
4. PWAが原因なら実装と試験を同時に修正する。

### 旧プリセットが表示されない

9.0.0では名前付きプリセット機能を意図的に廃止している。旧localStorageデータは削除しないが、UIから参照しない。サーバー側バックアップはなく、復元や新形式への移行を約束してはならない。

### GitHub Pagesが失敗した

Pages設定、対象ブランチ、最新コミット、主要ファイルの存在を確認する。原因を直すPull Requestを作り、成功確認前に公開完了と報告しない。

## 10. ロールバック

1. 直前の正常版と問題を起こしたPull Requestを特定する。
2. 履歴を破壊せず、問題コミットをrevertするPull Requestを作る。
3. キャッシュ対象が戻る場合でも新しいキャッシュ名を使う。
4. 自動試験、ローカル確認、マージ承認を経て公開する。
5. Pages、公開版、実機を再確認する。
6. 原因、影響、復旧版、再発防止を個人情報なしで記録する。

保存形式を更新済みの場合、コードを戻しても削除されたlocalStorageは復元されない。この影響を先に説明する。

## 11. 選択肢管理

選択肢、初期値、UI表示名、出力語句、色チップは、`src/unified-catalog.js`、`src/catalog.js`、`src/anime-shooting.js`、`src/outfits.js` を正本とする。身長連動、寸法区分、推定カップは `src/body-measurements.js` を正本とする。変更時は `tests/unified-prompt.test.mjs`、`tests/body-measurements.test.mjs`、`tests/assets.test.mjs` を同じ変更単位で更新し、自動試験と公開版のコピー結果を照合する。別形式の選択肢台帳は運用しない。

9.0.0では撮影項目を運用対象から外す。コードに旧候補が残る場合でも、UI、生成文、保存対象、実行時依存へ到達しないことを契約試験で確認する。Excelを含む別形式の選択肢台帳は利用、更新、照合しない。

## 12. 定期点検

少なくとも担当交代時と大きな変更前に次を確認する。

- GitHubの所有者・保守担当・不要権限
- `main` の保護設定とPages配信元
- Node.js要件と自動試験
- 公開版番号、Service Workerキャッシュ版、保存形式
- iPhone Safariでの主要操作
- GPTの編集権限、共有状態、非公開バックアップ、ハッシュ
- 公開文書に禁止情報が混入していないこと
